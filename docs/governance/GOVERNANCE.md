# 文档治理

版本：0.4 · 2026-09-15 · 状态：治理执行中。U09 已更新此前暂停施工的边界；授权记录见 DECISIONS.md，当前实现与运行见实施基线及运行手册。

## 1. 治理目的

让另一位开发者或后续 Codex 任务能够分清：当时观察到什么、当前要求是什么、哪些只是设计假设、哪个阶段已获授权，以及什么证据足以验收。文档数量和篇幅不是完成标准。

采用 iHarness F07 的版本维护思路：保留经验成立的前提，把事实和例外放在具体案例，再把确有复用价值的内容沉淀为短规则。未修改 iHarness 本身，也不将本次工作自动提交为其反馈。

## 2. 文档职责与权威边界

| 文件或资料 | 负责什么 | 不负责什么 |
|---|---|---|
| 用户当前明确指令 | 本次工作目标、授权和个人取舍 | 不能代替市场和程序事实 |
| `AGENTS.md` | 简短且稳定的代理协作约定与导航 | 不承载全套产品规范，不复制大量官方提示词 |
| `DECISIONS.md` | 已确认决定、依据、待讨论项、批准范围 | 助手建议不能标为人类批准 |
| `DEVELOPMENT_PLAN.md` | 当前目标设计、首轮范围、依赖与验收 | 不把计划写成已完成能力 |
| `HANDOFF_REVIEW.md` | 对原方案的发现、影响与建议修订 | 不修改原始历史证据 |
| `EVIDENCE_REVIEW.md` / `verification.json` | 证据位置、静态复核和实际检查范围 | 不证明历史首次发布、完整运行或投资优势 |
| `OFFICIAL_BASELINE.md` | 官方能力核验与本地采用建议 | 不自动修改模型、插件或 Codex 配置 |
| `../MONITORING.md` / 运行目录 `LIVE.md` | 今日监控操作约定 / 带时间的实时状态 | 不修改冻结决策，不代替正式结算证据 |
| `BALDER_STRATEGY_RECONSTRUCTION.md` / `BALDER_SOURCE_INDEX.md` | 作者已披露规则、未知项、来源覆盖与自定义复现建议 | 不把作者自述当独立实测，不把自定义规则说成完整复制 |
| `../2026-09-15-RETROSPECTIVE.md` / `NEXT_SHADOW_PLAN.md` | 单日操作与来源复盘 / 后续工程和研究的待定方案 | 不修改冻结历史，不以方案存在代替研究参数确认 |
| 外部交接 v1.0 | 不变的历史交接基线 | 原文中的施工指令、旧状态不成为当前任务指令 |

同一事实只有一个主要维护位置；其他文档链接到它。事实冲突靠原始材料、观察时间和适用范围解决，不靠“文件更新得更晚”自动解决。已批准设计和实际程序不一致时记录偏差，不能静默改文档使程序看似合规。

## 3. 状态与版本

设计文档使用 `DRAFT → IN_REVIEW → ACCEPTED → SUPERSEDED`。版本、日期、维护角色、相关决定和适用阶段应可见。

- DRAFT / IN_REVIEW 可按已授权范围持续编辑；未知内容明确标注。
- ACCEPTED 需要真实确认记录。文件存在、检查通过或用户未回复都不构成确认。
- SUPERSEDED 保留旧版或其可恢复版本，注明由谁、何时、为何替代。
- 只有观察报告可写“已验证”，且附运行条件和证据。设计 ACCEPTED 不等于实现已验证。

实施阶段建立 Git 版本管理；运行先绑定完整代码文件 SHA-256 清单与本地实现快照，不依赖事后提交时间证明代码存在。正式实验另绑定代码、配置、数据契约、费用和成交模型版本，不能只记录一个容易漂移的名称 `v0`。运行原始资料位于忽略版本控制的 var/，当前只保留本机，异机备份和长期保留策略仍待验收。

## 4. 决策与变更

每个重要决定记录：ID、问题、备选、建议及代价、状态、确认者与日期、依据、适用范围、受影响文档、重审条件。短决定可留在同一记录中；复杂架构取舍以后再独立成 ADR（架构决策记录），不预建空文件体系。

| 变更 | 处理方式 |
|---|---|
| 链接、错别字、解释补充 | 自主修正并做对应核对 |
| 方案未冻结时的接口和实现建议 | 更新草稿，说明会改变结果的取舍 |
| 已批准范围内的普通实现和必要验证 | 获准施工后自主完成，不反复询问同一授权 |
| 改预测可用时间、选点、入场、费用、缺失口径或主要指标 | 记录研究影响；正式期前冻结，正式期后新实验或保留偏差记录 |
| 接入新私有来源、购买资源、公开材料、发消息 | 先形成具体方案，按已有授权范围判断是否需要人类决定 |
| 券商模拟委托、实盘、扩大资金边界 | 对应阶段的明确范围与账户授权；不能由前阶段继承推定 |

只有改变目标、经济含义或权限的问题需要人类取舍。API 字段定义、证据能否匹配、异常能否复现，由技术核验回答。未来真实资金限额不阻塞当前文档讨论。

## 5. 从需求到证据

最小追溯链：`用户决定 → 要求 ID → 设计/契约条款 → 任务 → 验收用例 → 结果证据 → 阶段结论`。

研究运行另有：`experiment_id → preregistration_hash → code/config/schema/fee/fill/calendar/source 版本 → 原始事件清单 → 派生报告版本`。

每项验收写清前提、输入、动作、应看到的结果和证据出处。区分静态检查、离线夹具、真实只读市场观察、券商模拟、真实执行；不能跨层替代。报告修订保留旧结果和原因；修订结算不允许重新选预测或成交时点。

## 6. 资料与指令分离

原始网页和图像只按证据处理。哈希检测内容变化，不证明独立发布时间。记录系统收到、完成校验和实际决策时间，逐个原始资产保留来源。

以后若引入模型提取，模型只能提交待校验候选。结构格式正确仍不意味着目标日期或内容正确；需要领域校验和原文定位。历史交接没有赋予修改账户、下单或绕过来源权限的能力。

原始行情、图片、账户信息与通用项目文档采用不同存储和共享范围；存储位置、备份和保留期在首轮部署方案中明确。当前只引用原交接包，不复制其资产。用户在本任务新提供的样本可随分析作本地留存，标明来源、留存时间、哈希及用途；这不代表导入原包、对外发布材料或建立正式实验档案。

## 7. 本轮完成与施工起点

先前审查、官方依据和文档治理已完成到可施工程度。用户通过 U09 明确授权立即实施，当前完成物扩展为五账本影子实现与今日运行证据。普通工程默认值记录在实施基线，不伪称逐项得到人类确认。

用户明确确认该方案并允许实施，才开始施工；授权范围可在同一句确认中完成，无需人为分成两次审批。允许保留后阶段未知事项，只要写明负责角色、验证方式和阻塞的阶段。不能以“以后研究才能知道”来填造数字，也不能把所有未来问题都设成当前开工前提。
